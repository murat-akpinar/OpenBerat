### 🚀 Features

- The design, the decisions, and the container skeleton ([65ed744](https://github.com/murat-akpinar/OpenBerat/commit/65ed74439e5e57e607b7aae4433474f7b3037956)) — OpenBerat is an identity-aware proxy: Keycloak federates to Active Directory, and a user reaches only the applications their AD group membership allows, through a portal and without a VPN. This commit is the whole design and none of the runtime — eighteen ADRs, the target architecture with its request path and ports, the requirements and the roadmap, alongside the per-container directories whose Dockerfiles are still commented stubs. Phase 1 is a lab that verifies the architecture against a real directory before a line of code is written.
- The kill switch gets an index, and the documents stop contradicting each other ([3dc2f33](https://github.com/murat-akpinar/OpenBerat/commit/3dc2f33fa854d8052600db738d3640a753e520ae)) — The five-second kill switch was unimplementable as written. oauth2-proxy keys its Redis sessions by ticket rather than by user, so nothing in the design could find the session belonging to a `sub` — the second half of the two-place revocation was a sentence, not a mechanism, and without it the switch degrades to `cookie_refresh`, five minutes. ADR-0019 gives the backend a `sub → session` index, written on the cache-miss path where it already holds the cookie, and fixes the revocation order at four steps. The claim it rests on is not verified: Phase 1 gains VERIFY (4), and if the session key turns out not to be derivable from the cookie, the fallback and the revision of ADR-0016 are written down rather than discovered later.
- *(lab)* Wildcard certificate — :443 enabled, INSTALL.md first draft ([467b877](https://github.com/murat-akpinar/OpenBerat/commit/467b877e1ed1b20e004de7ae817d75aeb3ee668b)) — The first Phase 1 item. A self-signed wildcard for *.apps.example.local is generated on the lab host (certs/ stays gitignored), the :443 server block is enabled, and INSTALL.md starts with the steps exactly as executed — prerequisites, certificate, name resolution, .env, start. Verified live: the presented certificate carries the SAN wildcard and validates without -k, HTTP/2 200 on two wildcard hosts, :80 → 301. Which CA signs the production certificate stays open (docs/06).
- *(lab)* The login chain works end to end — VERIFY (1) answered ([3a87730](https://github.com/murat-akpinar/OpenBerat/commit/3a877300886a089f734a9efc887d831e10ba41d9)) — The realm export, the oauth2-proxy configuration and the portal + Keycloak server blocks, brought up together on the lab host until a browser login completes and the portal serves the user their page.
- *(lab)* The double hop costs 126 microseconds ([f1afcad](https://github.com/murat-akpinar/OpenBerat/commit/f1afcadbe771d88ccfc02bd25e4ed09338181f63)) — ADR-0002 spends an extra internal hop on every request: nginx cannot chain a second auth_request, so the chain runs inside the backend and the PDP calls oauth2-proxy rather than nginx calling it directly. That decision has been carrying an unmeasured bill since the design. It is 126 microseconds.
- *(lab)* The websocket ran for eight minutes after its group was gone ([c3e9175](https://github.com/murat-akpinar/OpenBerat/commit/c3e9175576a998e77afdf9815ac1b4caa969b93e)) — An active connection is authorised once, at the upgrade, and never again. Measured: one echo connection carrying a frame a second, plus an HTTP poller on the same cookie and the same authz target. The HTTP path was cut 292 s after labuser lost the group, at the cookie_refresh boundary; the connection carried 500 exchanges over 499 s, 489 s of them after the group was gone, and returned every frame in ~0.2 ms. This is ADR-0016's exclusion measured rather than asserted.
- *(migrations)* Initial schema for application, entitlement and audit ([f748b14](https://github.com/murat-akpinar/OpenBerat/commit/f748b14ee523ca4bbea19dc94f3d2bb7089763bc)) — The three v1 tables, applied and checked against a real Postgres 17 by `backend/tests/schema.rs`. `audit_event` is partitioned by month with the PK on `(id, ts)` and a DEFAULT partition, and starts with the summary columns it can never gain later.
- *(store)* Apply migrations at startup, exit if one fails ([398c869](https://github.com/murat-akpinar/OpenBerat/commit/398c869b2af48252cca9485c73bfaf1fec2621fb))
- *(policy)* The decision function and its URI normalisation ([e4d4a57](https://github.com/murat-akpinar/OpenBerat/commit/e4d4a5700129dfe1fba7c67d6225a50b5babc10a)) — `decide` takes the raw `X-Original-URI` and normalises it inside itself rather than trusting a caller to have done it. The one hole in this design is somebody matching the raw string — `/%61dmin/`, `//admin/`, `/x/../admin/` and `/ADMIN/` all walk past a `/admin/*` deny rule while the upstream serves the same page — and a signature that cannot express that closes it. Fourteen tests, every row of the `docs/05` normalisation table among them; each guard was removed in turn to see the test that covers it fail.
- *(store)* Entitlement query and the audit write path ([7aebe4f](https://github.com/murat-akpinar/OpenBerat/commit/7aebe4f027c0639909032f69c36e5dd9696be855)) — `rules_for` returns the application and the rules that apply to one user on it in one call — the whole of what a cache entry is filled from. Two things it gets wrong silently, so both are commented and both were checked by mutation: a rule with a NULL `application_id` applies to every application (`docs/05` rule 4), so the id cannot simply be equality-matched; and expiry is deliberately not filtered in SQL.
- *(api)* GET /decide, the endpoint nginx asks on every request ([2de98bc](https://github.com/murat-akpinar/OpenBerat/commit/2de98bce2aca583dfd13f15a560744f99d95d9ad)) — Forwards the cookie to oauth2-proxy, takes the verified identity from that response, and decides. Identity is read from oauth2-proxy's answer and from nowhere else, so a forged `X-Auth-Request-Groups` on the way in cannot reach the decision even with nginx out of the picture — there is a test for that rather than a claim, because it is the classic hole in this architecture and network isolation should not be the only thing closing it.
- *(cache)* The decision cache, and the audit summaries that leave it ([1e2a866](https://github.com/murat-akpinar/OpenBerat/commit/1e2a8661f98ff40126825737682dbc545077ed7b)) — Keyed on `(cookie_hash, app_slug)`, holding the identity and the rule list rather than a verdict — the matched pattern cannot be part of a key, because finding it is the query the cache exists to avoid. Every request, hit or miss, is evaluated against the full rule list, so a deny can never be skipped by two paths colliding on one key.
- *(session)* The sub -> session key index the kill switch needs ([be3996c](https://github.com/murat-akpinar/OpenBerat/commit/be3996c5c7ae944f33ecd96bfa18feb612fb9361))
- *(nginx)* The PEP wiring — decide subrequest, header rewrite, error pages ([631f799](https://github.com/murat-akpinar/OpenBerat/commit/631f7991a279b2382b43b81b4c00dea0540efe42)) — Everything between the browser and an application: `auth_request /decide`, the identity lifted off its response and written upstream, the login and "no access" redirects, and the local page an outage answers with.
- *(api)* /healthz and /readyz, the only visible difference in an outage ([ed3bf6f](https://github.com/murat-akpinar/OpenBerat/commit/ed3bf6f7c596a572ea23808dab72569c8a3f4d1a)) — The fail-closed rule hides its own failures. With Postgres unreachable `/decide` answers 403 for every request, and from outside that is indistinguishable from a policy that denies everyone — same status, same page, same silence. These two endpoints are where the difference lives.
- *(nginx)* Rate limits, and an access log that says who and why ([0fae06c](https://github.com/murat-akpinar/OpenBerat/commit/0fae06c97ad7b97337464781cf3aee365ceb9951)) — One log line now answers both questions a denial raises: `user="labuser" deny="explicit_deny" id=4f10…`, and the `audit_event` row carrying the same id has the rest. Verified end to end rather than assumed — the id in the nginx line and the id in the row were compared.
- *(breakglass)* The second nginx configuration, and the rehearsal ([e37f178](https://github.com/murat-akpinar/OpenBerat/commit/e37f178f0821f9e7063be51920e52b6f9e852f33)) — ADR-0017 accepts a single point of failure in front of every internal application. What makes that acceptable is not a promise of uptime but a rehearsed way back, and this is it: a complete second nginx configuration shipped inside the same image, serving the applications directly while the identity chain is repaired.
- *(admin)* The management plane — /api/me, application CRUD, two guards ([8b54232](https://github.com/murat-akpinar/OpenBerat/commit/8b54232fed62bd766389a09c4b214bc254bbd0be)) — `/api/admin/*` is not protected by the entitlement table: the portal is open to every authenticated user, so if reaching it were enough then anyone could grant themselves entitlements. Both guards therefore live in middleware and not in the handlers — ADMIN_GROUP membership, and an `Origin` check on anything state-changing. A guard written per handler is a guard somebody forgets on the handler added at 3 a.m., and the one it is forgotten on is the one that grants entitlements.
- *(admin)* Entitlement mapping, and a portal list that cannot disagree ([3311180](https://github.com/murat-akpinar/OpenBerat/commit/3311180f538416243c405d0761b0c7078bfe2052)) — `/api/admin/entitlements` maps AD groups to applications, allow or deny. The four field checks are duplicated from the schema on purpose: the constraints are the real boundary, and these are so a typo comes back as a sentence instead of a 503 with a constraint name in the log.
- *(admin)* Generate the application blocks, and let nginx install them ([0a968fc](https://github.com/murat-akpinar/OpenBerat/commit/0a968fcfa430495a68d7fc679b7371b188577ce0)) — An admin defines an application through the API and it becomes reachable a couple of seconds later, with nobody editing a file and no image rebuilt — which is what F-13 asks for and what ADR-0011 was written to make possible.
- *(portal)* The portal lists the applications a user can reach ([90b6da8](https://github.com/murat-akpinar/OpenBerat/commit/90b6da89ffb8394a2e3a03a3322073602a9f34f7)) — The portal draws what /api/apps returned and nothing else: that list is policy::decide run over the rules the PEP itself applies, so a button is never a second opinion about access. An empty list and a failed call say different things — /api/apps answers 503 when Postgres is down, and drawing that as "you can reach nothing" would tell a user their access was revoked in the middle of an outage.
- *(frontend)* The "no access" page names the application that refused ([86ff3dd](https://github.com/murat-akpinar/OpenBerat/commit/86ff3ddb7f3387a69e2b5a9a07b341fa5c95cacf)) — The route was wired in Phase 3; what landed on it was a placeholder saying the real page arrives in Phase 5. It now names the refused application, says what to do about it, and links back to the portal's list of what the user can reach.
- *(frontend)* Vendor the alpine csp build, measured against a real csp ([b4f9039](https://github.com/murat-akpinar/OpenBerat/commit/b4f90391fe4fe6ab24e4b306242d301794f8b550)) — The standard Alpine build loads under `default-src 'self'` and then evaluates nothing: `window.Alpine` is present, every binding keeps its fallback text, and the page reports `script-src blocked eval` twice. Measured in a browser rather than on the lab, since a CSP is enforced by the browser and not by nginx. So `@alpinejs/csp@3.17.1` is vendored at `frontend/src/vendor/alpine.js`, with its npm integrity hash and the upgrade procedure in the README beside it.
- Federate the realm to the lab ad, and pin the cache policy that keeps it live ([f53a8be](https://github.com/murat-akpinar/OpenBerat/commit/f53a8bed6342ae322baf8a40c2f846a6f3ca66e5)) — Keycloak's LDAP provider only reads group membership live at NO_CACHE. Measured against a real Samba AD DC: with the policy at DEFAULT, a group removed in AD survived a brand-new login — fresh session, fresh token — and was still in the claim three minutes later, with nothing bounding the delay. So ADR-0006's "Keycloak is not a staleness layer" is a property of that one setting, not of Keycloak, and NO_CACHE joins cookie_refresh as a line that fails silently: the login keeps working, the entitlements stop tracking AD. MAX_LIFESPAN bounds the staleness to its own window; DEFAULT does not bound it at all. TODO.md VERIFY (2).
- *(frontend)* Give the portal a visual language before the login theme ([30e9e92](https://github.com/murat-akpinar/OpenBerat/commit/30e9e9240006015dca0008053a587e09ff252e5e)) — The three existing pages shared a stylesheet but not a face. They now carry one: tokens at the top of portal.css in a paper/ink/gold palette taken from what a berat is — a sealed warrant granting a right — one logo.svg serving as both header mark and favicon, and a gradient rule repeated on all three pages so they read as one product rather than three files. Done before the login theme so that theme has something to inherit.
- *(keycloak)* Our own login theme, and the image is no longer stock ([385ba2e](https://github.com/murat-akpinar/OpenBerat/commit/385ba2e75d556fc07ef81f5f5168e04285b20e86)) — The one screen every user meets first was stock Keycloak on a second hostname — a different product to anyone looking at it. The theme is a child of keycloak.v2 that overrides no template: theme.properties, one stylesheet, one message. Copying the .ftl files in would mean owning FreeMarker across Keycloak upgrades, and a template that stops matching its theme breaks the one page nobody can route around.
- *(admin)* The audit record is readable, and a filter it cannot honour is a 400 ([7198452](https://github.com/murat-akpinar/OpenBerat/commit/719845263baa199e5d7b6d82d3eff11c8755d47a)) — `GET /api/admin/audit`, filtered by actor / app / decision / reason / since / until and paged with a `(before_ts, before_id)` keyset cursor. Both design decisions come from the same rule: an audit viewer must never answer with a list that is quietly not the list that was asked for. An unrecognised filter name or value is refused rather than dropped, because a dropped filter widens the result and the admin then reads "these are the denials" off a page with allows on it. And the cursor is a keyset rather than an OFFSET, because rows arrive at the head of this ordering while an admin pages through it — OFFSET repeats page one on page two, and once the N-04 retention job deletes from the tail it skips rows instead.
- *(admin)* The decision explained, and checked against the PEP that made it ([c8d05e5](https://github.com/murat-akpinar/OpenBerat/commit/c8d05e5176adcb94a2ebc5505856736aad273e14)) — `GET /api/admin/explain?user&groups&host&path` answers why a request would be decided as it is: the verdict, the path it was actually matched against, and every entitlement row it walked with matched/expired marked beside it.
- The kill switch, and the signed-in session it could not see ([f321480](https://github.com/murat-akpinar/OpenBerat/commit/f3214801cc0b5f6b3862ba8a31bc0a9caf6c97e7)) — The four steps of ADR-0019 behind `POST /api/admin/kill/{sub}`: Keycloak `logout-all`, the session keys from the index, that user's cache entries, then the index entry. Measured end to end on the lab at **0.085 s** against N-03's 5 s, with each step checked for the mark it should leave rather than inferred from the end state — three of the four are invisible from outside, and a kill switch that silently skips one still looks like it worked.
- Logout, and the token that lives inside what it deletes ([f97b19a](https://github.com/murat-akpinar/OpenBerat/commit/f97b19a9bcd6b6bc32f2b85f914ab19dd91d5e0c)) — All three logout steps run inside POST /api/logout now (docs/02), not one here and two in the browser afterwards. Written the second way the middle step silently did not happen: Keycloak will not end a session without an id_token_hint, the hint comes from oauth2-proxy's backend_logout_url, and that token is inside the session the backend had just deleted. Measured on the lab, the IdP session survived its own logout and the next request signed the user back in with no password.
- *(nginx)* Security headers, the TLS floor, and a renewal that drops nothing ([40a11dd](https://github.com/murat-akpinar/OpenBerat/commit/40a11ddcbc029fc2595376bfe958dc358dc49d44)) — Security headers and TLS settings move to two http-level includes, tls.inc and security.inc, shared with the break-glass configuration so the two cannot drift. The certificate goes with them: no server block carries a copy any more, including the ones ADR-0011 generates. The trap the box is really about is add_header — nginx inherits it by replacement, so one header set in a location drops every header above it, and the three locations that relay the refreshed session cookie by hand are the portal, the admin API and protected.inc, which is every application. CI now fails the build if a location with an add_header does not pull security.inc back in.
- *(backend)* The restore that needs no admin, and the dump flag that broke it ([7add0bb](https://github.com/murat-akpinar/OpenBerat/commit/7add0bbe9fa3c8ebe1e61e7d179cc66bbd626fda)) — Backup is one database: `pg_dump`, plus `certs/` and `.env`. Everything else on the host is derived or in the repository, and this box is where that became true rather than merely claimed — the generated nginx blocks were written only by a mutation handler, so a restored database gave every application a hostname nginx had never heard of. The backend now renders them at startup too (ADR-0011), which makes the shared volume derived state and keeps it out of every backup.
- *(backend)* Audit retention, and the month that could not be partitioned ([653c713](https://github.com/murat-akpinar/OpenBerat/commit/653c713bb3eecb297231143f3129fb25ae34192d)) — N-04 was open because the retention period is the operator's — KVKK asks for a stated period, not for ours. ADR-0022 answers it as a mechanism with a default instead: AUDIT_RETENTION_MONTHS, 12, and a month leaves the database as a dropped partition rather than a pass over every row in it. audit_event has been partitioned since 0001_init.sql with only the default partition; the backend now creates the current and next month on a daily tick and drops what falls out of the window. The default partition is never dropped — it is what stops an INSERT for an uncovered month failing off the request path — so expired rows in it are deleted at the same cutoff.
- *(backend)* /metrics, and the outage that a 403 hides ([cdcbeb9](https://github.com/murat-akpinar/OpenBerat/commit/cdcbeb96938ec485919067faad0d45028bc13764)) — `GET /metrics` answers in Prometheus text format with the four numbers Phase 6 asks for: decision latency, decisions by outcome and reason, cache hit rate, and the audit summaries that never reached Postgres. Hand-written rather than a client library — the exposition is four line shapes, and the counters were already named in the code (`Deny::as_str`, `store::audit_dropped`), so a registry to hold them would have been a second vocabulary for the same words.

### 🐛 Bug Fixes

- Thirteen design errors found before any code depended on them ([9e85ecf](https://github.com/murat-akpinar/OpenBerat/commit/9e85ecf3fc2fd41adcd3d41c00552254cc7e8495)) — The pre-code review found thirteen design errors; fixing them today is a text edit, fixing them in Phase 3 would have been migrations. The worst three: a flat docker network let a compromised upstream reach the backend, Redis and Postgres directly (split into edge/core, nginx the only member of both); the session cookie was forwarded verbatim to every upstream (now stripped before proxying, ADR-0015 corrected); and logout's third step had no caller — nothing ever dropped the cache, so a replayed cookie outlived logout by a TTL (now POST /api/logout, run in kill-switch order before the sign-out redirect).
- Six more design gaps found before any code depends on them ([382f94c](https://github.com/murat-akpinar/OpenBerat/commit/382f94c71d3c762fc794552d493996f75d3388f1)) — A cache entry could leave the cache by four roads — TTL, LRU eviction, logout, kill switch — and only TTL expiry flushed its audit counters: the kill switch would have erased the audit trail of the very user under incident response. The /decide response contract never said how nginx learns the identity it rewrites upstream (response headers, the only channel auth_request offers). Admin mutations and kill switch use had no stated audit at all — now F-14, the structured log stream in v1. A failed sub->session index write silently produced unkillable sessions — now a fail-closed DENY, written before the ALLOW it enables. Keycloak's public hostname was never pinned — auth.apps.<domain>, inside the wildcard, session cookie stripped, name reserved in the ADR-0011 generator. And VERIFY 4 never asked whether the Redis key survives cookie_refresh.
- The realm export carries no secrets, and the portal auth path is pinned ([01e1596](https://github.com/murat-akpinar/OpenBerat/commit/01e159693d7fab8b78e37b17c30dbfde45388148)) — The repository is public and keycloak/README.md said a UI change is re-exported and committed — which would have committed the OIDC client secret with it. The export is now scrubbed by rule; how the real secret is injected at import (env substitution or a post-import step) is a Phase 1 verification. And the portal host's auth mechanism was never pinned: its auth_request targets /oauth2/auth directly, not /decide — authentication without policy — which also means a portal-only user never enters the kill-switch index, a consequence now stated where the decision is.
- *(nginx)* A user in many groups was locked out by the 4k header buffer ([072e6a5](https://github.com/murat-akpinar/OpenBerat/commit/072e6a5c9e5307035bb303d2c8944783bc6a1947)) — The cookie size problem the Redis session store was chosen to solve is gone — the session cookie stays 192 bytes from 1 group to 800, never chunked — but the 4 KB limit moved rather than disappeared. Every group name comes back comma-joined in one X-Auth-Request-Groups, nginx reads a response header block into a single proxy_buffer_size buffer (one page), and auth_request maps the resulting 502 onto a 500 for the client. Ramped on the lab: clean at 100 groups, locked out between 100 and 200, with a passing nginx -t and no warning in any log — a total lockout of exactly the accounts an enterprise has most of.
- *(nginx)* The login redirect lost half of the query string ([6a48b02](https://github.com/murat-akpinar/OpenBerat/commit/6a48b02b92769ee2e8bb4708a77778a380ca37cb)) — The return address went into `?rd=$scheme://$host$request_uri`, and nginx cannot percent-encode it, so the client's own `&` started a new parameter of /oauth2/start. Measured: `/index.html?a=1&b=2` came back as `/index.html?a=1` — a 200, the right page, and everything after the first `&` silently gone. A deep link into a protected application would suffer that after any session expiry. An injected `rd` arrived as a second one; not exploitable (the first wins, `whitelist_domains` sits behind it), but the client was writing into the query string of a request it never made.
- .env.example was missing three variables the stack cannot start without ([b15e6b3](https://github.com/murat-akpinar/OpenBerat/commit/b15e6b37f353f562158658553a4cc3e998e1e6d8)) — docker-compose.yml reads eight variables and .env.example offered five. A fresh clone copying it to .env and running `docker compose up` gets an empty OAUTH2_PROXY_COOKIE_SECRET (oauth2-proxy refuses to start), an empty OPENBERAT_CLIENT_SECRET (the OIDC client secret Keycloak resolves at import) and an empty LAB_USER_PASSWORD — compose substitutes an empty string for an unset variable rather than complaining, so the first symptom is a container that will not come up.
- *(install)* Three steps only worked on the host that wrote them ([4d9e2f2](https://github.com/murat-akpinar/OpenBerat/commit/4d9e2f254ae97246839113c8d93e89184b79de7b)) — INSTALL.md said every step had been executed on the lab host, and they had been — on a host that already had the directory, the secret and the password the document tells you to create. Replaying §1-§4 from a clean checkout, with nothing but the file, broke three times before the first login.
- *(lab)* Samba needs a kernel the lab host does not have ([ae872d2](https://github.com/murat-akpinar/OpenBerat/commit/ae872d22a3ea1c5c8241fc3b7a4a1b313198fb6b)) — Bringing samba-ad up for the first time failed twice. The first one was ours: `hostname: ad` with `AD_DOMAIN=ad.example.local` gives the DC and the domain the same NetBIOS name and Samba refuses to provision. It is now dc01 in example.local — the pair docs/03 already documents, which also makes its example DNs literally correct.
- *(admin)* A comma in an AD group name reaches the management plane ([c5a531b](https://github.com/murat-akpinar/OpenBerat/commit/c5a531b03569ba9c83fa8322334bfd4e05af4246)) — The group list travels comma-joined in one header and is split back apart in the backend, so a single group named `Payroll,OpenBerat-Admins` arrives as two and the second one is ADMIN_GROUP. Measured end to end on the lab: an ordinary portal user in that one group got `admin: true`, a 200 on /api/admin/applications and a 201 on a wildcard entitlement — a grant covering every application, present and future. It cannot be closed on this side, because oauth2-proxy flattens the claim array before the request arrives; the control is the Keycloak group filter, which ADR-0008, docs/05, INSTALL.md and both READMEs now call mandatory rather than advisable.
- *(oauth2-proxy)* The second login flow that takes the first one's cookie ([374c9ff](https://github.com/murat-akpinar/OpenBerat/commit/374c9ffa4ee823f4aa4233e585af47f12bbfe009)) — A login on the lab answered 403 "Unable to find a valid CSRF token", and retrying worked. One page load starts more than one flow — anything that 401s reaches @signin and mints a CSRF cookie holding that flow's PKCE verifier — and with one cookie name for all of them the second start overwrites the first. The callback then redeems the code with the wrong verifier (Keycloak: invalid_grant, 500) or, if the other flow finished first and cleared the shared cookie, finds nothing at all (403).
